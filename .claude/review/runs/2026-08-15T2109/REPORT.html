Fix tonight

One line, two files, and it is the only thing here that is remotely exploitable

Critical · reachable in production

Both frontends pin next@15.1.0, which has a published RCE

client-web/package.json:34 and admin-web/package.json:18 pin Next.js to an exact version — not a range — so the lockfile resolves next@15.1.0 and no patch has ever reached it. That version sits inside GHSA-9qr9-h5gf-34mp — remote code execution via the React flight protocol, vulnerable >=15.1.0-canary.0 <15.1.9. Both apps run next start server-side in containers, so the vulnerable renderer is the one serving flowvidco.com.

The fix: set next and @next/eslint-plugin-next to ^15.5.23 in both packages (four lines total), pnpm install, then pnpm -r typecheck && pnpm -r test && pnpm release:verify. React is already ^19.0.0 resolving to 19.2.6, which 15.5 supports — no major bump, no code change expected.

A second critical advisory, GHSA-f82v-jwr5-mffw — authorization bypass in Next.js middleware (>=15.0.0 <15.2.3), also matches, and client-web/middleware.ts does exist. But that middleware performs no authorization: it returns 410 for archived courses and 308 for legacy redirects. Bypassing it renders an archived course page instead of a tombstone. Real, worth fixing with the same bump, not the headline.

The full picture from pnpm audit is 3 critical, 49 high, 35 moderate, 10 low. Nine of the high advisories are also next, so the same bump clears most of the top of that list.

One other dependency deserves the same trip: adm-zip carries a high advisory and sits directly on a user-upload path. backend-api/package.json:39 allows ^0.5.10, resolving to 0.5.17, and it parses attacker-supplied archives at avatar.controller.ts:145 (new AdmZip(buffer) on an uploaded buffer) and SimulationService.ts:3327. Check the resolved version against the advisory when you do the Next bump. The other runtime names in the high list worth a pass: undici, fastify, drizzle-orm, ws.

The slow avatar and the jumping b-roll

Two reported production symptoms, traced by five agents to two root causes

These were reported after the main audit, as the highest-priority items: the Anam avatar "comes up very, very slowly", and b-roll clips "jump to the wrong place". Both now have a mechanism. Neither is where the obvious guess would put it.

The avatar: nothing ever hands the session back

P1 · root cause · measured

The saved Anam persona is thrown away on every start, so every session pays to rebuild it

An agent built a timing harness against the vendored SDK — no real key, no network — and measured the whole chain. On the stateful happy path, where the stored personaId is used, /avatar/start is one vendor round-trip with a 118-byte body. When the persona is dropped and the request falls to the ephemeral path, it becomes three round-trips on a small account and six on a large one, carrying a 29,705-byte persona body that Anam must reconstruct server-side every single time.

That is a 1→6 hop expansion and a 250× body growth, per open. At a realistic 400–900 ms per vendor call, it is 2.5 to 6 seconds of pure backend serialisation before the browser can even begin its WebRTC join. Fixing this one collapses the common case from six hops back to one.

The discard happens at avatar.controller.ts:197, and it has an origin: commit b06feb4, "smooth video→sim transition, per-voice circle waves, avatar video knowledge + live Anam defaults". It is a regression, not an original design — which is good news, because it means there is a known-good shape to return to.

The framing that matters: the vendor round-trips dominate the time, but the number of them is ours. Exactly one call — POST /auth/session-token — is unavoidable. Everything else in the measured 15-hop table is work this repo chose to do per-start and can precompute, parallelise, cache or skip.

A correction, and it was mine. Mid-investigation I found that avatar.controller.ts:238 is a one-line stub — app.post('/api/v1/avatar/end', async (_request, reply) => reply.send({ ok: true })) — with no session-termination function anywhere in anamService.ts. I escalated it as the likely root cause: an accumulating concurrency-slot leak. I was wrong, and the agent refuted it from the vendored SDK's own type surface.

The backend never creates an Anam session. POST /auth/session-token returns a bare string; a sessionId first exists only when the browser calls startSession, and the SDK raises MAX_CONCURRENT_SESSIONS_REACHED from that call, not from the mint. So an unused token holds no slot. A normally-closed popup does not leak either — AvatarConversation.tsx calls stopStreaming() on unmount, on unload and on leave, and tearing down the transport is the release mechanism in this SDK. There is no termination endpoint to implement: none exists on CoreApiRestClient. And orphans are bounded anyway, because maxSessionLengthSeconds is already set to 600 s on both branches. The stub survives as a P3 tidy-up, not a P1.

Worth stating plainly because the escalation was confident and specific, and confident and specific is exactly how a wrong finding costs a day of someone's time. The agent checked the dependency instead of the codebase, which is what settled it.

The frontend's related finding stands but shrinks with it: client-web/components/avatar/AvatarPopup.tsx:47-71 does drop a resolved session token when the popup closes mid-fetch, without releasing it. That wastes a mint and a couple of vendor round-trips — a P2 cost issue, not the P1 slot leak it was filed as.

backend-api/src/services/avatar/anamService.ts

The b-roll: the viewer plays the clip list it fetched on first load, forever

My own first hypothesis was that dragging a clip in the editor updated state while the player held a stale copy — the commit message on sections.controller.ts:407 says in the author's own words that "a drag, a trim, a move and an undo/redo restore all splice THIS response into the editor's section state". The agent killed it: the editor does not use useProjectPlayer at all. It is a separate player whose b-roll position is a prop recomputed every render, with a drift-resync effect firing at 8–10 Hz, so an edit self-heals within about a second.

The real answer is that there is no single bug. Five separate mechanisms displace a b-roll clip, and they are ordered here by how well each explains the symptom on its own.

A b-roll's position is an absolute second, and the content underneath it moves

backend-api/src/services/buildPlayerConfig.ts:555-575 (true b-roll) · :581-591 (clip overlays) · runVideoTranscode.ts:99

Corrected after review — an earlier version of this report described this wrongly, and the distinction changes the fix. The two overlay kinds are positioned by different mechanisms. True b-roll (track='broll') is emitted with its stored global_offset_sec, unchanged; nothing recomputes it. Clip overlays (type='clip') are the ones resolved against a running total of video_files.duration_sec — and that column is client-seeded on upload then overwritten with the real ffprobe value at transcode, so those genuinely drift.

For true b-roll the defect is subtler and worse: the position is an absolute second that never moves, while the content beneath it does. Re-transcode a main video to a slightly different length and the clip still fires at second 47 — but second 47 is now a different moment in the story. The number was never wrong; it just stopped meaning what the author intended. That is why no amount of recomputation fixes it, and why the real question is a product one: should a placement be pinned to the clock, or to the thing it was illustrating?

P1

One section can be emitted twice, at two different offsets, into the single list the player searches

backend-api/src/services/buildPlayerConfig.ts:558 vs :591

The two filters are not disjoint. broll_clips takes s.track === 'broll' && !s.clip_source_audio_id and uses the stored global_offset_sec; clip_overlays takes s.type === 'clip' && s.clip_source_video_id and uses a computed vidOffset + s.start_sec. A row that is both track='broll' and type='clip' satisfies both and appears in both arrays — at two different positions. The player then concatenates them and takes the first match.

P1

The section query has no deterministic order, and b-roll is sorted by a column that is not its position

backend-api/src/services/buildPlayerConfig.ts:191

Sections come back ordered by asc(start_sec) only — but for a b-roll, start_sec is an in-point into the source clip, almost always 0. So every b-roll row ties, and Postgres is free to return them in any order, differently between requests. This is what makes the symptom intermittent and hard to reproduce: which of two candidate clips the player picks can change on a refresh. It also disagrees with the editor's own (sort_order, start_sec) ordering, so the preview and the viewer can disagree about the same project.

P1

The player's b-roll logic is frozen at mount, and the config behind it does get replaced

client-web/components/viewer/useProjectPlayer.ts:2712 · ViewerPage.tsx:33-81 · lib/firebase.ts:114

Three verified links. One — onTick is useCallback(fn, []), frozen forever, and every b-roll, cutaway and overlay call site reads config.* off the closed-over parameter. There are zero occurrences of configRef in the file, while the segment and timeline branches of the same function correctly use segmentsRef.current. Two — ViewerPage's polling effect declares [projectId, authLoading, getIdToken] as its dependencies and calls setConfig(data). Three — getIdToken is a plain inline async () => {...} with no useCallback, inside a context value rebuilt on every render of the auth provider mounted at app/layout.tsx:60, above every page. A cross-tab sign-in is enough to give it a new identity. So the config is replaced while the player stays mounted — and the b-roll logic never sees it. The viewer plays the clip positions it fetched on first load even after a backend correction lands.

P1

When two clips overlap, which one plays is decided by array position

client-web/components/viewer/useProjectPlayer.ts:2351

.find() over [...broll_clips, ...clip_overlays] with no tie-break and no overlap rule. Harmless if overlaps cannot happen — but two already-confirmed findings create them: jobs/video.generate.ts:58 appends a second timeline section on a retry, and queue/pgBossDriver.ts's singletonKeyFor returns a dedup key for crop only, so duplicate pending video_generate jobs are never collapsed. Duplicate section plus positional tie-break is a complete path to a clip playing where it should not.

P2

Only one of the two doors that create a b-roll section enforces that it has a position

backend-api/src/controllers/v1/sections.controller.ts:256, :296 vs broll.controller.ts:27

broll.controller.ts requires global_offset_sec: z.number().min(0), and the AI generation job cannot produce a null either — target_global_offset_sec is notNull() and zod-validated. The generic POST /sections is the one door left open: it validates only video_file_id, start_sec, end_sec and type, then writes global_offset_sec ?? null with no rule that a track='broll' row must carry a position. A null then becomes second zero silently at four read sites, including buildPlayerConfig.ts:571 and exportPlan.ts:426,446-447 — so such a clip sits at the very start of the preview and of the exported video. Add the invariant at the write; fail loud instead of ?? 0 at the read.

P2

Neither POST nor PATCH /sections has a runtime schema at all

backend-api/src/controllers/v1/sections.controller.ts:380

The ordering guard compares numbers that may arrive as strings, and PATCH mass-assigns the raw request body via { ...rest }. Twenty-five of twenty-seven controllers use safeParse; this one, which owns timeline positions, does not.

P2

Overlapping b-roll is neither prevented nor defined

backend-api/src/db/schema.ts:634

No constraint, no documented rule. So "what should happen when two b-roll clips overlap" is answered independently, and differently, by each consumer that reads the data — the player, the editor and the export planner. That is why the same project can look correct in one surface and wrong in another.

P2

Two more of my hypotheses were killed by reading the code, and are recorded so they are not re-investigated: the PATCH /sections handler is correct — it builds { ...rest } and never writes omitted fields, so a drag cannot null an offset. And TimelinePanel.tsx:1041 returning global_offset_sec: null is correct too — that branch is for main-track sections, which are positioned by start_sec within their video and have no global offset by definition.

Fix order — avatar. Keep the persona stateful so the common case is one round-trip instead of six; that single change is the answer to the report. Then move the post-mint display lookups off the response path, and put a timeout on every Anam call. Then fix the double-mount guard so two starts do not both mint. Then the cheap parallel wins together: Promise.all the independent lookups, drop the duplicate projects read, skip the transcript scan on the fast path, unblock the audio pre-warm, and add preconnect. Then muted plus an explicit .play() with a real error surface, and the 2-second spinner timer. Add timing instrumentation early — the harness measured the shape of the chain, but no production number exists yet.

Fix order — b-roll. The anchoring change is a product decision, not an engineering one, and it is now taken: placements move to a stable host anchor (main segment id + local offset) with ripple semantics, rolled out expand/contract behind a placement mode, dual-read, and no silent backfill — mapping today's absolute second onto today's segment would canonize placements that are already wrong. Everything else proceeds independently: make the two filters disjoint, give the section query a total order (start_sec ties for every b-roll, which is why the symptom is intermittent), add runtime schemas on the write path, and give video_generate a real lease and a durable job→section uniqueness constraint so a retry cannot append a second section.

Note the shape of it. The player-side findings are real, but they are what stops a fix from reaching a running viewer — not what put the clip in the wrong place. Fixing only the player would leave the positions wrong; fixing only the backend would leave already-open viewers showing the old positions until reload. Both halves are needed, in that order.

Architecture: what to actually change

Ranked by value per unit effort, from a dedicated advisory pass

The standing belief was that headless capture is blocked by a 600-second synchronous cap. That premise is wrong in two ways, and correcting it changes the fix. Export is already async with polling (export.controller.ts:63); the 600 is a per-section container kill timer, min(600, 90 + durationSec × 6), which only reaches 600 past 85 seconds of content. And deterministic offscreen rendering — the obvious first suggestion — is already implemented: beginFrameBackend.ts drives HeadlessExperimental.beginFrame against a virtual clock.

The real cost model: 1920×1080 at 30fps means round(dur × 30) frames plus 30 warmup, rasterised by SwiftShader software GL, with sections captured strictly sequentially. A 15-second section is 450 frames inside a 180-second budget — 0.2 s/frame allowed against roughly 2 s/frame actual. Every step of the per-frame path (rasterize → JPEG → base64 over a pipe → parse) is linear in pixels, which is what makes the first two items below work.

1

Give each queue its own concurrency, and stop over-committing the box

Split localConcurrency per queue instead of reusing the crop number, drop EXPORT_CAPTURE_CPUS below the host count, fix expireInSeconds. Pure config, instantly revertible, and nothing else measures reliably until the host stops being ~3× over-committed.

~1 day · ~10 lines · file: queue/pgBossDriver.ts:17-19,54
2

Instrument the capture, then decouple capture resolution from export resolution

Capture at 960×540 and upscale during encode. The scale filter already exists at containerCaptureProvider.ts:150 — it is currently fed identical input and output dimensions. Roughly 3–4× on the live blocker. Do the instrumentation first so every later decision is evidence-based.

~2 days · ~3–4× throughput
3

Add a route-drift test and delete the dead tsoa config

174 backend /api/v1 paths against 145 client call sites, with nothing generating the client and nothing checking it. A ~150-line AST test asserting client ⊆ server converts a silent failure class into a pnpm test failure. The cheapest permanent win in the plan.

~1 day · ~150 lines · no controller changes
4

Decouple the clock rate from the readback rate

Another ~2× with no change to simulation dynamics. The trap: naively "capture at 15fps" halves the virtual clock step and silently changes what the simulation renders. Keep stepping at 30Hz and screenshot every Nth frame — driver.ts:226-237 already separates stepFrame from captureFrame.

~2 days · needs a careful driver test
5

Move transcode and the two podcast render jobs onto the worker

One array element in pgBoss.ts:22 plus cascade verification. Directly closes the incident class the comment above that line already documents. The effort is in the testing, not the writing.

~2–3 days
6

Content-addressed clip cache keyed on the immutable sim revision

Repeat exports become nearly free. The identity primitives already exist — posterIdentity.ts and a configHash computed at exportPlan.ts:264-285 and currently used only as a PRNG seed. Clips key on exportId today, so nothing is ever reused. Docked slightly for stale-hit risk.

~3 days

The contract review found the drift item 3 is meant to catch, and more of it than expected. shared/src/generated/, tsoa.json and the root generate script together describe a codegen pipeline that has never existed — the directory name is the only thing suggesting anything generates that 1,667-line client. Concretely: SimMeta's exported shape has nothing to do with what the server writes, and the frontend already routes around it with unsafe casts; CourseViewSchema and LessonViewSchema exist specifically to validate that boundary and are never called, while the real fetch uses an unchecked cast; AvatarPersonaConfig is declared independently on both sides instead of in shared/, and the two copies have already diverged. There is also a fully zod-validated course-authoring API in courses.controller.ts with zero consumers anywhere — worth deciding whether that is unfinished or abandoned before it is maintained by accident.

Explicitly recommended against. Parallel segment capture — the box is already CPU-saturated and the compose file records an OOM at 908 MB. A warm browser pool — incompatible with the --network none ephemeral-container isolation at containerRunArgs.ts:132-176; keep the isolation and buy throughput with pixels and caching instead. TSOA for the contract — it is Express-only and would force all 27 controllers at once, where a shared/-rooted contract migrates per route.

If you do only three things: items 1, 2 and 3. About four days, each independently revertible, and together they address the live blocker, the saturation and the silent-drift class.

The review fleet audited itself

Because a wrong premise manufactures confident findings

This repository maintains its own 25-agent review fleet with a written protocol, a shared stack-truth file and an enforcement hook. That infrastructure exists because a previous generation of it believed the backend was Express over MySQL when it is Fastify over Postgres. A dedicated audit ran against it during this review and found 37 issues — 5 blocking.

  • Three agent files still name a fourth LLM provider that does not exist. llm-pipeline-reviewer, security-reviewer and dependency-auditor all count Groq among the LLM providers. There are three; groq-sdk is speech-to-text only. The stack file says so explicitly, so these agents contradict their own source of truth — and one of them was reviewing that exact subsystem during this run. This is the Express/MySQL failure shape, alive again.
  • Six new guard bypasses, all reproduced. The most important is glob expansion: segments() at fleet-guard.mjs:110 splits on ||, &&, ;, | and newline, and the secret check runs before the shell expands .en*. Also: a single & is not a segment boundary, $(...) and backticks are not boundaries, awk is allowlisted with system() unguarded, and sed --in-place evades the -i test. Together these collapse an allowlist back toward a denylist.
  • The per-agent guard was not armed during this run. Frontmatter hooks require workspace trust; only the project-wide secrets floor was live. Confirmed empirically — agents wrote memory into three different .claude/agent-memory/ roots depending on their working directory. The secrets floor did hold, and git diff --stat is empty: no tracked file was modified by anything in this review.
  • Two areas are named by zero agent definitions: ops/ship/** (13 files sequencing PR → CI → merge → deploy, landed two commits ago) and backend-api/src/scripts/** (29 scripts that run against production data). Both were covered here only because they were added to a dispatch prompt by hand.
  • Recommendations from the previous audit were never applied. Four of the drift items found this time were already reported on 2026-08-14. The backend test count was flagged then as 128→131, never changed, and has since drifted to 136.

Separately: podcast-saas/CLAUDE.md is stale boilerplate describing GoDaddy Node.js Hosting with managed MySQL and npm start, for a pnpm monorepo on Postgres deployed by Docker Compose. It is not inert — it was auto-loaded into this session's context as project instructions while the review was running. It is the highest-leverage single file to delete or rewrite.

How much of this survived being attacked

Every P1 was handed to an agent whose only instruction was to refute it

Each P0 was to be checked by three verifiers with different lenses — correctness, guard, reachability — and each P1 by one, all told to default toward refuted when evidence was thin. No P0s were filed against the product, so the pass ran 32 verdicts over the P1 set: 31 CONFIRMED, 1 REFUTED, 0 UNCERTAIN.

The refutation is worth reading, because it shows the standard being applied. database-002 claimed the migration runner parses DATABASE_URL differently from the app, truncating dotted usernames — a plausible-sounding Supabase-pooler bug. The verifier opened the installed driver, found that postgres@3.4.9's own parseUrl does exactly what db/index.ts:12-24 does, then ran the real driver against a pooler URL and printed the resolved options: the username came through whole. The finding did not survive contact with the actual dependency.

A 97% confirmation rate is a good sign, but read it with its limits: a single verifier per P1 is a thinner adversarial pass than the three-lens treatment a P0 would have received, and the run produced no P0s to exercise that path. Two of the fifteen reviewer domains did not complete the verification handoff at all — config-deploy failed its structured return after five attempts, and test-quality returned an empty set through that channel. Both wrote their findings to disk, so their results are in this report and in the run directory, but they were not adversarially verified. Treat those two domains as one confidence level lower than the rest.

Separately, my own three orchestrator claims went through the same mill and fared worse than the fleet's: two refuted, one confirmed but downgraded. Both refutations are recorded above rather than quietly dropped.

Is any of this actually novel?

An advocate and six blind prosecutors, run separately — the answer is mostly no, and that is worth knowing

A dedicated agent surveyed the whole system for mechanisms worth protecting, starting every candidate at "this is obvious" and making it earn its way up. It found 2 survivors out of 30 candidates, both rated only moderate. Nothing scored strong.

Then, to test that verdict rather than trust it, six more agents ran blind — they never saw the first agent's reasoning and were told not to look for it. Their only job was the opposite one: establish what the field already does and prosecute the case that each area is the obvious solution. The result is close to unanimous: one decisive and five strong obviousness cases, and not a single area where the standard approach demonstrably fails. Every residual difference they conceded, they explicitly labelled small.

Two independent passes, opposite instructions, converging: nothing here clears a confident novelty bar. That is a useful answer. It is also a cheap one to have — the alternative was finding out in a lawyer's office.

What genuinely is distinctive is narrower and more interesting than "revolutionary". The most notable examples, each small and specific:

  • Capability negotiation with a counterparty that cannot negotiate. Every standard negotiation protocol assumes two live processes that can each state what they support. Here one side is a published, frozen artifact that cannot answer — so what it supports is decided and recorded when it is published, not when it connects.
  • Migration-runner drift detection. Because the runner's file list is hardcoded in source, an audit extracts that list from the code and set-diffs it against what is on disk. The prosecutor for that area — the one that returned decisive obviousness overall — noted that no off-the-shelf migration tool does this. The most ordinary area produced the most distinctive residual.
  • Prefetch admission tied to the primary stream's own buffer. Speculative preparation of an upcoming simulation is allowed only once the video is buffered far enough ahead to reach it — coupling two unrelated resources that are normally managed independently.
  • A cover that the player cannot inspect. Standard first-frame gates cover the seam with a surface the player owns. Here the outgoing cover is a frozen — but still audible — sandboxed document whose pixels the parent cannot read, which is what forces the whole evidence-based reveal discipline in the first place.

This is an engineering novelty assessment, not a legal opinion — patentability depends on a real prior-art search, claim drafting and jurisdiction, which is an attorney's work. By deliberate instruction the assessment cites no specific patents, numbers, assignees or claim text; it describes the field only in general terms.

The investigation's most valuable output was not a candidate at all. Chasing the strongest lead is what surfaced the unenforced reproducibility guarantee and the mislabelled frame evidence above — both filed as P1 engineering findings. Looking hard at what you might own turned out to be a good way to find out what you have not verified.

What this review did not establish

The limits are part of the result

  • Findings are verified unless the text says otherwise. The exceptions are the two domains named above, plus P2/P3 findings generally — the adversarial pass covered the P1 set only.
  • One engine only. Firefox is not installed here, so all Playwright runs were Chromium. The configs' own comments explain why three engines matter — requestVideoFrameCallback and WebGL context-loss diverge between them.
  • Docker was not running, so buildx --check, the deploy scripts and the export-worker smoke test could not execute locally.
  • Nothing touched production. No remote command, no migration, no database connection beyond local PGlite in tests. release-cli coverage-report refused to run without SMOKE_* inputs, which is correct behaviour, and it was left refused.
  • Coverage was measured for the backend only. client-web reports 54.7% statements but its vitest config declares no coverage scope at all, so that number counts only files its tests happen to import — a different kind of unreliable from the backend's, and not one this run untangled.
